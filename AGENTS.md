# Webex CLI

A CLI for Webex Admin, Calling, Contact Center, Devices, Meetings, and Messaging APIs, plus an MCP server and agent skills.

## Project Layout

- Go CLI at repo root (`main.go`, `cmd/`, `internal/`), built on the Go SDK in `pkg/`
- `codegen/` — Python scripts that generate the operation table (`pkg/webexops`) from Postman collections
- `cmd/admin/`, `cmd/calling/`, `cmd/cc/`, `cmd/device/`, `cmd/meetings/`, `cmd/messaging/` — each area's `commands.go` builds its commands from the operation table at startup (`internal/apicmd`)
- `cmd/*.go` — handwritten root/area/auth/config/MCP entrypoints
- `cmd/mcp/` — MCP server (stdio or loopback HTTP)
- `cmd/**/custom_*.go` — handwritten commands for operations the table cannot describe (multipart uploads, downloads, search)
- `testdata/golden/` — every command's flags and help, and the request each API command sends; `cli_golden_test.go` checks them
- `extension/` — Claude Desktop DXT package (`make extension`)
- `skill/` — agent skill files; each area’s Command Reference is regenerated by codegen
- `site/` — Astro Starlight docs (GitHub Pages)

## Code Generation Pipeline

The generated `pkg/webexops/zz_*.go` files must not be edited by hand. Change `codegen/generate_cli.py`, `internal/apicmd` (how operations become commands), or a `custom_*.go` file instead.

```bash
# Full pipeline (download + generate operations + generate skills + build):
make refresh

# Regenerate from existing committed collections:
make codegen && make build

# Download collections only:
make download

# Go and codegen tests; rewrite the golden files after an intended change:
make test
make golden
```

`make codegen` runs `extract_api_spec.py`, `generate_cli.py`, and `generate_skills.py`.

The golden files pin the published CLI. A change to codegen or `internal/apicmd` that is meant to keep commands the same must pass `go test -run Golden .` unchanged; one that changes them needs `make golden` and a reviewed diff. The weekly workflow runs `make golden` after a collection refresh.

For command naming exceptions, edit `codegen/naming_overrides.py`; see
`docs/command-migration.md` for naming and compatibility conventions, and
`docs/command-inventory.md` for the reviewed refresh inventory. These route-based
overrides feed both generated commands and skill references. Use `custom_*.go`
and the generator skip lists when the request itself needs handwritten handling.

No API key is required — collections are fetched from the Webex Public Workspace via Postman's public gateway (`codegen/download_collections.py`).

APIs missing from those collections are described by hand in `codegen/supplemental/`, which downloads never touch. Each file joins the downloaded collection its `info.name` names, and a route the download also documents is taken from the download. The private AI Agent Studio routes behind `cc ai-agent*` live there; see `codegen/supplemental/README.md` before adding to them.

A weekly GitHub Actions workflow (`.github/workflows/update-collections.yml`) downloads collections, regenerates commands and skills, and opens or updates a PR. It also has `workflow_dispatch`. If GitHub has disabled it for inactivity, re-enable it under Actions after merging workflow fixes.

## Build

```bash
go build -o webex .
make check   # build + go vet
```

Module path: `github.com/Cloverhound/webex-cli`. Go version is the `go` directive in `go.mod`.

## Releasing

Releases are handled by a GitHub Actions workflow triggered by pushing a tag.
Do **not** run `goreleaser` locally — it requires secrets (e.g. `WEBEX_CLIENT_ID`)
that are only available in CI. Version and OAuth defaults are injected via ldflags.

The same workflow publishes the npm packages: `npm/stage.mjs` turns goreleaser's
`dist/` into `@cloverhound/webex-cli` plus one `@cloverhound/webex-cli-<os>-<cpu>`
package per binary, and `npm/publish.sh` publishes them with provenance. It
authenticates with npm trusted publishing (configured per package on npmjs.com
for `release.yml`), or with the `NPM_TOKEN` secret when that is not set up.
Tags with a prerelease suffix (`v0.X.0-rc.1`) publish under the `next` dist-tag.

To check the packaging without secrets, run `goreleaser build --snapshot --clean`
with dummy `WEBEX_CLIENT_*` values, then `node npm/stage.mjs` and `npm pack` the
folders in `npm/build/`.

```bash
git tag v0.X.0
git push origin v0.X.0
# Then set the release notes via gh:
gh release edit v0.X.0 --title "v0.X.0" --notes "## Improvements
* ..."
```

## Key Files

- `cmd/root.go` — Root cobra command, global flags (token, org, output, debug, dry-run, paginate, 429 retries, region, cc-region)
- `cmd/auth.go` — Auth subcommand (status, list, switch, set-org, clear-org)
- `cmd/login.go` / `cmd/logout.go` — OAuth PKCE and device login
- `cmd/mcp.go` / `cmd/mcp/` — MCP serve/stop, tools, resources, usage log
- `cmd/update.go` / `cmd/postinstall.go` / `cmd/skillupdate.go` — self-update and skill install
- `internal/auth/` — Token storage (OS keyring, credentials file fallback), OAuth, device login, org resolution
- `npm/` — npm wrapper package, staging, and publish scripts
- `internal/client/capture.go` — `--changeset` capture (beta): records a create, update or delete of a writable catalog type in a change set instead of sending it, and refuses every other request, because Webex Admin Studio refuses a whole file over one operation it cannot apply. Field-level checks (fixed fields, required fields, value rules) are left to Studio's import
- `internal/client/` — Request builder (JSON and multipart bodies), CLI pagination, and the CLI's use of `pkg/webexapi` with its process-wide flags; `SDK()` gives SDK packages a transport set up the same way
- `internal/appconfig/` — Config file (`~/.webex-cli/config.json`)
- `internal/config/` — Process-local flags (token, org, debug, dry-run, retry, regions and hosts)
- `internal/output/` — JSON/table/csv/raw formatting
- `internal/audio/` — Binary download from pre-signed URLs (no Webex token)
- `internal/aiagent/` — The private-API notice, and `pkg/aiagent` with this run's login and hosts

### Go SDK (`pkg/`)

Other Go programs import these, and Webex Admin Studio is built on them. They hold no process-wide state and take a context on every call. Keep CLI concerns (flags, output, the config file) out of them.

- `pkg/webexapi/` — HTTP transport: 401 refresh, 429 Retry-After, structured errors, fail-closed list paging; `Hosts` for every data region and Contact Center data center; org ID conversion; the Contact Center pacer
- `pkg/webexops/` — Generated operation table: one exported `*Operation` per API call (route, parameters, body fields, paging, CLI names), and `Call`
- `pkg/resource/` — Object types as data: fields, JSON paths, write mode, and the operations (`Route`) each type uses. API facts only; presentation belongs to the program
- `pkg/catalog/` — The object types. A type is `Managed` (writable) only once its writes are proven on a live tenant; its tests check every route's operation, method and parameter bindings. `match.go` finds the type a write request or a change set target names. How Studio names types in Terraform config lives in Studio, not here
- `pkg/webex/` — Reads and writes objects from their definitions
- `pkg/guard/` — The write protocol: conflict check, read-back, stop after a failure
- `pkg/changeset/` — Change set file format (types, recording rules, validation, JSON Schema)
- `pkg/aiagent/` — AI Agent Studio: agent token lookup, credential redaction, `Call`
- `pkg/fakeapi/` — The fake Webex the SDK, CLI and Studio tests run against

Live Webex behavior that the catalog encodes (full-object Contact Center PUTs, read-by-filter work types, Contact Center rate limits) is recorded in Webex Admin Studio's AGENTS.md, where it was found.
- `codegen/supplemental/` — Hand-maintained Postman collections for APIs not in Cisco's collections
- `codegen/extract_api_outline.py` — Postman → normalized CLI names
- `codegen/extract_api_spec.py` — Postman → enriched API spec (params, body fields)
- `codegen/generate_cli.py` — API spec → operation table (`pkg/webexops/zz_*.go`)
- `internal/apicmd/` — Builds `webex <area> <group> <command>` from the operation table
- `codegen/generate_skills.py` — API spec → Command Reference blocks in `skill/<area>/SKILL.md`
- `codegen/diff_spec.py` — Changelog between two spec snapshots (used by the weekly workflow)

## Documentation checks

Update README, the site area pages, and handwritten skill guidance alongside API changes. Run `make codegen` for all six generated skill references, `python3 -m unittest discover -s codegen -p 'test_*.py'` for naming checks, and `npm run build` in `site/` for documentation validation. Keep command documentation focused on behavior, compatibility, and known limitations. Put PR validation and work-session results in the PR, not repository documentation; do not include personal identities or tenant test data.
