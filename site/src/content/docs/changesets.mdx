title: Change Sets (beta)
description: Propose Webex changes as a portable file for Webex Admin Studio to review and apply.

:::caution[Beta]
Change sets are in beta. The file format may still change, and Webex Admin Studio may refuse an operation it cannot apply.
:::

A change set file proposes Webex configuration changes without making them. It names each object by its API route and Webex ID, and each field by its path in the API's JSON. Webex Admin Studio imports change sets for review, plan and apply. An agent with a read-only login can write one.

## Recording a change set

Run ordinary write commands with `--changeset <file>`, or set `$WEBEX_CHANGESET`. For each write, the CLI:

1. finds the object type the command writes, and refuses anything Studio cannot apply;
2. reads the object the command names;
3. records only the fields whose values the command changes, keeping the values it read as preconditions.

Nothing is sent to Webex, so recording works in read-only mode too. Only creates, updates and deletes of the types Studio applies can be recorded: `webex changeset types` lists them with their commands, and `webex changeset types <type>` lists a type's fields.

With `--changeset`, an update body describes the proposed changes. Send only the fields you intend to change, even for a Contact Center update: omitted fields stay as they are, and lists are replaced whole. Do not apply a proposal by removing `--changeset`, because a direct Contact Center update needs the complete object.

```bash
webex changeset new desk.changeset.json --title "Boulder front desk" \
  --rationale "Ticket IT-4812" --on-behalf-of admin@example.com

webex --changeset desk.changeset.json calling hunt-group update \
  --location-id <loc> --hunt-group-id <hg> \
  --body '{"callPolicies":{"noAnswer":{"numberOfRings":5}}}'

webex --changeset desk.changeset.json cc team create \
  --body '{"name":"Boulder Desk","siteId":"<site>","teamType":"AGENT","teamStatus":"IN_SERVICE","active":true}'
# {"action":"create","changeset":"…","id":"new:boulder-desk","recorded":"op-2"}
```

**Recording rules**

- **Creates:** a create prints a placeholder ID such as `new:boulder-desk`. Later commands in the same change set can use it in flags and bodies.
  - An update to the new object folds into its create.
  - A delete withdraws the create.
  - A `new:` ID must belong to a create of the same type, under the same parent.
- **Repeat edits:** edits to one object merge into one operation, even when its update and delete use different routes, as a Contact Center queue's do. The latest value wins, and the first precondition is kept. A later create that an edit refers to moves ahead of the edit.
- **Unchanged values:** a value equal to the one Webex holds is not recorded. For types whose updates send only changed fields (Webex Calling), setting a field back withdraws the change recorded for it. A Contact Center body that repeats a field leaves an earlier change to it in place; use `webex changeset drop` to remove one.
- **Ignored fields:** an update records only the fields the object type models; the rest, such as `id`, `version` or `links` in a body copied from a read, are listed as `ignored` in the output.
- **Org:** a request for an org other than the change set's is refused, whether its path, query or body names it.
- **Deletes:** an update to an object the change set deletes is refused. A delete records no snapshot of the object, so `validate --live` can only report that it is gone.
- **Refused:** anything that is not a create, update or delete of a type Studio applies, such as a bulk save, a purge, an action like answering a call, or a read-only type like a person. Also refused: query parameters other than the org (put the fields in `--body`), a create or update without a JSON body, a delete with a body, a write to an object that cannot be read, and file uploads. With `--dry-run`, nothing is recorded: the request is printed instead.
- **Not checked here:** field rules are left to Studio's import, which refuses a change to a field that is fixed once the object exists, a cleared field, a create missing a required field (see `webex changeset types <type>`), and a value Webex does not accept. Studio's import preview lists any such operation.
- **Files:** a new change set file can be read only by its owner. Saving keeps the mode of an existing file.

## Commands

| Command | What it does |
|---|---|
| `webex changeset new <file>` | Starts a change set for the current org, with optional `--title`, `--rationale`, `--author`, `--on-behalf-of` and `--link name=url` |
| `webex changeset show <file>` | Summarizes operations by intent, with before → after values |
| `webex changeset validate <file> [--live]` | Checks the structure. With `--live`, it also re-reads every updated or deleted object and reports drifted preconditions, missing objects, and objects it could not read; any of them makes the file invalid |
| `webex changeset intent <file> <id> <summary> [op-id…]` | Adds or rewords a plain-language intent and assigns operations to it |
| `webex changeset drop <file> <op-id> [path…]` | Removes an operation, reverting what it proposes, or with paths, those field changes from an update. A create that another operation refers to waits until that operation is dropped |
| `webex changeset meta <file>` | Changes `--title`, `--rationale`, `--author`, `--on-behalf-of` or `--link name=url` after `new`; an empty value clears one, and `--link name=` removes a link |
| `webex changeset types [<type>]` | Lists the types a change set can record and their commands; given a type, its fields, which ones a create needs and which are fixed |
| `webex changeset schema` | Prints the JSON Schema |

The MCP server offers the same features through `webex_propose` and `webex_changeset`. Both are available in read-only mode. `webex_propose` accepts only `calling` and `cc` write commands, the areas with types Studio applies.

## File format

```json
{
  "format": "webex-changeset/v1",
  "metadata": {
    "id": "cs_20261103T150000Z_1a2b3c4d",
    "title": "Boulder front desk",
    "createdAt": "2026-11-03T15:00:00Z",
    "rationale": "Ticket IT-4812",
    "author": { "type": "agent", "id": "webex-mcp", "onBehalfOf": "admin@example.com" },
    "links": { "ticket": "https://tickets.example.com/IT-4812" }
  },
  "scope": { "orgId": "<org UUID>" },
  "intents": [{ "id": "front-desk", "summary": "Create a Boulder front desk team" }],
  "operations": [
    {
      "id": "op-1", "intent": "front-desk", "action": "create", "handle": "boulder-desk",
      "target": { "api": "cc", "route": "/team", "display": "Boulder Desk" },
      "body": { "name": "Boulder Desk", "siteId": "<site>", "teamType": "AGENT" }
    },
    {
      "id": "op-2", "action": "update",
      "target": {
        "api": "webex",
        "route": "/telephony/config/locations/{locationId}/huntGroups/{huntGroupId}",
        "params": { "locationId": "<loc>", "huntGroupId": "<hg>" },
        "display": "Front Desk"
      },
      "changes": [{ "path": "callPolicies.noAnswer.numberOfRings", "before": 3, "value": 5 }]
    },
    {
      "id": "op-3", "action": "delete",
      "target": { "api": "cc", "route": "/skill/{id}", "params": { "id": "<skill>" }, "display": "Old skill" }
    }
  ]
}
```

### Targets

- **`api`** is `webex` for `https://webexapis.com/v1` (Calling, Admin and other areas), or `cc` for the Contact Center API.
- **`route`** is the API route template.
  - Contact Center routes are relative to `/organization/{orgId}`.
  - An update or delete route ends with the object's ID placeholder. A settings update may target a route with no ID.
  - A create route names the collection.
  - Placeholder names do not matter when routes are compared.
- **`params`** gives a value for every placeholder.
- **`query`** holds other query parameters, which can select the object, as `userEmail` selects whose meeting preferences. The CLI never records one, and Studio does not apply it.
- **`display`** is a label for people.

### Operations

| Action | Carries | Meaning |
|---|---|---|
| `create` | `handle`, `body` | Create an object with this request body |
| `update` | `changes` | Set each `path` in the object's JSON to `value` |
| `delete` | — | Delete the object |
| `invoke` | `method`, `body` | Any other write, kept as sent. The CLI never records one, and Studio refuses it |

Each change carries a `path` and a `value`:

- **`path`** is a dotted path into the object's API JSON. Lists are replaced whole, as Webex replaces them.
- **`value`** is the new value. `null` clears a value; Studio does not apply clears yet.
- **`before`** is optional. It is the value the author saw, and `null` means the field was absent. An engine should not apply a change whose `before` no longer matches.

Any value `{"$ref": "<handle>"}`, in a body or a change, means the ID of the object that the create with that handle makes. A create must come before the operations that refer to it.

### Review

An exported change set may carry a `review` block with the plan it was reviewed against (`plan.hash`, `plan.commit`, `plan.plannedAt`) and any `approvals`. Importers display it but do not enforce it.
